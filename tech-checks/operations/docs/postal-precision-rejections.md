# Basic US postal precision and safe rejection reasons

Review artifact for `us_zip_precision_v1`. Implementation and verification use local synthetic data. No production recovery, provider call, deployment or production data write has been performed.

## Behavior and boundaries

[Geocodio's address standardization documentation](https://www.geocod.io/how-to-parse-and-standardize-addresses) states that basic geocoding removes the +4 from returned US postal codes. Accept that precision difference only when the ZIP5 is identical and every other existing address/quality/identity guard passes. When both values contain +4, the entire ZIP+4 must agree. This applies symmetrically to ZIP5/ZIP+4.

Source installation objects, original address strings, source revisions, provenance hashes and cache keys retain their full supplied ZIP+4. Numeric source ZIPs remain invalid. A provider numeric ZIP5 is accepted only for an integer from 10000 to 99999; shorter numbers cannot establish lost leading zeros and are rejected. Five-digit and hyphenated ZIP+4 strings preserve leading zeros. No non-US postal format, malformed code, different ZIP5, paid ZIP+4 field or enrichment is accepted.

Imported Census and basic Geocodio selectors, legacy SQL postal persistence/read guards, the native contract and automatic frontend estimates agree on this rule. Existing street/house/city/state, ambiguity, method, 0.9–1 accuracy, coordinate, source-current, Owner, GPS and identity protections remain in force. Original Owner Census adapters and both reviewed V2 property-proof implementations are unchanged. The two exact Edge bundles retain their existing nine and 22 files, respectively.

## Safe new-result diagnostics

New outcomes retain `status: no_match` with one allowlisted reason: `provider_empty`, `ambiguous_results`, `provider_warning`, `invalid_components`, `component_mismatch`, `formatted_address_mismatch`, `unsupported_method`, `low_accuracy`, `invalid_coordinates`, or `provider_rejected` (HTTP 422). Selection checks run in that order: expected/payload shape, count, warning, component shape, supplied-component agreement, formatted-address agreement, method, accuracy, coordinates. Census uses the relevant subset. Transport and account failures retain their existing provider-error codes.

SQL uses the existing reason arguments, cache columns and RPC signatures. No overload, expanded caller role or raw provider content is added. New helpers are private/service-only. An omitted reason continues to save the legacy `no_match` value; historical `no_match` still means that the cause is unknown. No backfill reclassifies historical failures. Read guards may suppress a stored success with a provably incompatible postal code but do not rewrite that stored row.

## One bounded historical recovery plan

The runnable migration supplies service-only `cos_imported_geocode_postal_retry_enroll(uuid,jsonb)`, `cos_imported_geocode_postal_retry_list_due(uuid,integer)` and `cos_imported_geocode_postal_ordinary_list_due(uuid,integer)`. The original ordinary v2 RPC is unchanged; the new ordinary wrapper prevents 80 exhausted/cancelled policy hashes from starving the next ordinary job. A genuinely stale marker restores revised-source/Owner work under the usual guards. The operator template defaults to rollback and requires a reviewed, explicit manifest. The first successful enrollment freezes the exact manifest for this policy version: at most 80 bindings and 80 distinct original full-address hashes. Replaying the identical normalized manifest is read-only; changing or expanding it fails. Shared addresses use one bound representative for provider work and retain normal guarded estimate sharing.

Before filling the manifest, use fresh native source-bridge reads and inspect existing Owner/GPS/identity guards. Include only exact current FIELD jobs with source ZIP strings matching five digits, a hyphen and four digits. Preserve full source/native revisions, provenance and address hash. Exclude held, invalidated, superseded, SHOP/UNKNOWN or otherwise ineligible bindings. Dedupe by the original full-address hash, never ZIP5 or unit name. A changed manifest requires a new review, not another invocation with a larger cohort.

For each candidate, the imported Census cache must be exact address/hash, terminal `no_match` with the historical unknown-cause reason `no_match`, and have no active request or lease. The shared Geocodio row must be absent or terminal `no_match` with the historical reason `no_match`, the same address/hash and no active request or lease. Fresh, safely diagnosed failures and newly admitted sources are not the historical recovery cohort. Enrollment fails atomically if any candidate is ineligible, successful, uncertain or inflight. Historical causes remain unknown; eligibility relies on source postal precision, not an invented old rejection reason.

Enrollment stores the frozen manifest, exact binding and before-images in private policy tables. It changes no cache status, attempt, request, source or credit. The existing cron reads the bounded enrolled cohort alongside a separate ordinary-reader wrapper that preserves the PR76 prefilter/order and excludes only currently blocked recovery hashes before the limit. For an enrolled hash, the handler prioritizes Census and retains the same fresh before/after source reads, four-request concurrency and 80-address sweep cap. Every claim/reservation independently enforces its own current binding, marker and account locks; reading a queue never grants an attempt.

At the first actual Census claim, the exact stored terminal snapshots must still agree. Only that real request and lease replaces the prior terminal status. The claim bypasses historical Owner no-match reuse for its enrolled binding, while retaining Owner inflight exclusion, source/Owner/GPS/identity checks and existing daily attempts/backoff. Plain cache resets are never part of recovery.

- Fresh Census success completes recovery without Geocodio spending.
- Fresh Census no-match may advance the marker to Geocodio only for that recorded request and still-current exact binding. The old Geocodio no-match remains visible until a real charged reservation is obtained.
- Changed/ineligible source or a new authoritative Owner/GPS state cancels recovery. The identical cancelled source binding cannot resume through ordinary retry RPCs. A genuinely revised binding or Owner request keeps normal current-source, budget and attempt controls without reopening the marker; that ordinary work is outside this recovery cohort. Normal Owner work retains priority and is not permanently blocked by a stale marker.
- Active retry phases prevent ordinary imported or Owner shared-address requests from bypassing the policy's attempt counters or Census-first ordering.
- Budget/account/attempt refusals do not overwrite a historical Geocodio no-match with a fake pending state. No reservation means no provider request or new charge.
- Actual Geocodio requests consume new, durable credits and retain the free-only 2,400 backend daily cap, 2,500 provider account cap and three-per-day limits. A policy counter additionally caps each provider at three actual claims total across days, so recovery cannot continue indefinitely through daily resets.
- Provider errors use the existing bounded backoff. Completed no-match, success or exhausted policy cannot reopen through marker replay. Prior credits are never refunded, daily counters/attempts are never reset, and existing success is never overwritten.

Use the cron receipt's additive `postalRetry` counters to separate recovered address results from ordinary sweep work; normal receipts without enrolled work retain their previous shape. Those counters count distinct lookup addresses, not physical units. Separately read the fresh map DTO and count distinct newly estimated current unit identities by provider to report recovered pins, including shared-address units. Report remaining new safe rejection codes, held/cancelled/exhausted bindings and newly charged credits. The fixed cohort is complete when all entries reach a terminal outcome; no new recurring schedule or expanded cohort is part of this operation.

Full imported integration tests run source bridge → database claims/reservations → injected provider response → native projection → frontend estimate, including Census ZIP5 success (zero Geocodio credits) and Geocodio ZIP5 fallback (one credit), while preserving full source provenance. All network provider results in tests are injected; no production lookup is needed.

It checks concurrent enrollment, claims, reservation credit serialization, changed-source publication denial, final-credit contention and unchanged queue definition. Never target a production server with this synthetic-schema test.
