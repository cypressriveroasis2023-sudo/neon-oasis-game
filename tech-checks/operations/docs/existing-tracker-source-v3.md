# Existing native equipment with exact Google tracker provenance

This is a local preparation and synthetic test artifact. It contains no production candidate rows, source admission, deployment, credential, permission expansion, provider lookup or quota reset. The reviewed baseline is source-equivalent PR83 (`3441e510`), composed with the independently reviewed agreeing-Shop projection (`122b9c6b`). It does not include the held generic creator or legacy address editor work.

## Contract

V1 mHelp imports and V2 tracker imports retain their current DTOs, immutable identities, source revisions, guards and administrator entrypoints. V3 applies only to an already-existing `equipment_unit` and a distinct, already-existing tracker UUID with the same exact complete label. It emits `schemaVersion: 3`, `sourceSystem: google_sheet_tracker`, and a typed `sourceRecordId`; it never contains or invents a ProductId.

The source ID is `google_sheet:<spreadsheet-id>:<tab-id>:<full-family>|<complete-number-and-suffix>`. Replacing the single `|` with a space must reproduce both native and tracker labels byte for byte. The source family must match the full family; V3 `variant` is null because the complete hardware suffix remains inside the identity token. Case, family/capacity, punctuation, decimal places, leading zeros and suffixes are never removed to establish a positive association. Unknown/complex grammars require separate review. Broad `cos_source_label` keys appear only in ambiguity denials.

The ordinary 18-field source binding is retained. Map projection additionally requires `COS_IMPORTED_NATIVE_SOURCE_IDENTITY_V3` with exactly the native UUID/complete label, tracker UUID/complete label, typed source identity, source revision, file/row hashes and native guard. V1 ProductId proof is not reused. This proof authorizes source address presentation only and is not a provider, camera, health, Owner or placement identity. Native `recordSource`, native UUID and health identity remain native; source classification is read-only presentation and writes no operational row. V3 Shop records expose family/variant only in the guarded map projection; the event tombstone stays compact.

## Admission and currentness

The new private `app_private.cos_existing_tracker_sources_admin_import_reviewed(uuid,jsonb)` is a SECURITY INVOKER that checks actual `current_user = postgres`. EXECUTE is revoked from PUBLIC, anon, authenticated and service_role. There is no bridge action, new service grant, schema USAGE, creator flag, target creation, withdrawal tool or administrative delegation. The old tracker revoker remains restricted to tracker entities when V3 equipment data exists.

Admission requires 1–250 explicit records, unique native/tracker/source IDs in the batch, an exact existing native/tracker graph, the current V3 native guard and either source absence or the exact prior typed revision. An existing mHelp source, metadata ProductId alias, matching mHelp catalog record or inventory ProductId association holds the record. Native/tracker UUID cross-collisions and duplicate/colliding full labels hold it. No operational record is written.

Private `sourceProvenance` has exactly `sheetId`, `tabId`, `fullIdentity`, `sourceRange`, and `sourceRangeSha256`. The A1 range must select one row. File/selected-row/range digests are mandatory. `sourceRangeSha256` is the immutable initial evidence anchor for the originally reviewed range, not a claim about the current edited range bytes. The source ID, A1 range and complete initial provenance are immutable after admission; a subsequent address revision commits its current file and selected-row bytes in `sourceFileSha256`/`sourceRowSha256` under CAS while retaining that initial anchor. Moving the source to another range or redefining the provenance requires separate contract review. The reviewed caller must verify the actual file/range bytes, whole-source uniqueness and full native/tracker graph from current evidence before constructing the input. A syntactically valid digest alone does not prove source truth. SQL does not fetch spreadsheets or authorize an unreviewed source row.

The V3 guard reuses the original native GPS/site/placement guard and adds exact tracker uniqueness, Owner claims (including conflicting/reserved aliases), location history, retired/current-reference metadata, archive endpoints, mHelp aliases and current tracker customer/metadata commitment. Any such authority or conflicting archive proof holds V3. It never uses an archive allowance to bypass the exact graph. All V1/V2 native guard semantics remain unchanged. Readers recheck V3 currentness; authority added without a native-row trigger still yields no current source or map projection on the next read. Native/tracker edits emit the normal source tombstone where applicable.

The importer uses READ COMMITTED and fail-fast SHARE locks on the relevant existing native graph/authority tables, then the established deterministic advisory/native/tracker/source lock order. A concurrent operational writer wins and admission fails with 55P03; roll back, refresh all evidence and retry separately. Same-source revisions use CAS, and an identical reimport preserves revision/event/timestamps. Private source provenance cannot be changed by a direct row update either.

Installation addresses pass the existing strict sanitation and supplied-component/hash checks. Free-only Census-first/Geocodio behavior, the shared 2,400-credit cap, caches, reservations, ordinary scheduling and historical V1 postal cohort remain unchanged. Current legacy Root/Owner/history/device guards still hold V3; V3 cannot carry a source-precedence override. Display-only bare camera grouping may use the existing source-only projection allowance after exact native source proof and absence of conflicting history; it creates no health association. The agreeing-Shop helper retains its verified native-provider proof requirement.

## Bounded SQL guard evaluation

Both source readers materialize only the requested organization/kind/UUID rows with the existing active/eligibility predicates before evaluating any native/competitor guard. Map projection performs the identical bounded argument validation directly instead of executing and discarding a second FIELD read. Empty, duplicate, unknown and invalid identity requests preserve their existing semantics. All competitor/Owner/history/archive checks still inspect the complete relevant evidence for each requested target.

The native/tracker change trigger similarly locks and materializes only affected active source rows selected by the original exact IDs or denial-only label concern. It evaluates guards on those candidate composites and keeps customer-change invalidation. An unrelated native/tracker write invokes no source-currentness guard; a health-only edit of a bound target checks one source without changing its source epoch. This changes evaluation order, not the currentness or collision policy.

Add `--performance` to the real PostgreSQL test to verify both 235 V1 + 235 V2 + 29 V3 with 800 native/tracker rows and a 250 V3 stress cohort with 1,052 native/tracker rows. Both contain complete unrelated Owner/history/catalog/source rosters. Guard-call assertions, rather than brittle wall-clock thresholds, require exactly the requested rows and zero guards for unrelated native/tracker writes. Migration hashes are captured from the bytes actually executed. Full-page stress requests retain the cost of all requested complete competitor checks.
