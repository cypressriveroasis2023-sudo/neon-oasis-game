# Scoped inventory review

`db/scoped_inventory_overlay.sql` is a deployment candidate, not an applied
migration. It depends on the existing upload overlay and Owner identity actor
gate. This PR does not install SQL, activate a source, or deploy application code.

The administrator-only review function also checks the existing Owner actor and
tenant authorization. Its inputs are the expected active upload hash, monotonic
scoped revision, unique request ID, derived-map provenance, and exact before/after
operations. Customer assignment corrections retain the existing binding. A
`replace_source_hold` operation replaces a current source ProductId without
asserting physical identity: it retains the previous batch and its history, sets
the new binding to null, and keeps candidate associations in review. An explicit
`inventoryOnlyReason: "no_sim"` requires SHOP and renders “No SIM / no current IP.”
It never imports an old endpoint. This restriction cannot be relaxed by the
assignment operation.

The bounded Sniper/CAM V categories and the four-family extension below are admitted. Category, lifecycle,
native IDs, endpoints, observations, activation and installation records cannot
be edited by these operations. When a customer changes, the old source-only
postal address is cleared from the new scoped row; it is retained in prior
evidence. No customer address becomes an installation location.

The base upload hash, payload hash, global timestamp, other records and tracker
authority timestamps stay unchanged. Each corrected row carries its own derived
evidence hash and source receipt time. Existing newer-source, Owner, location,
binding and collision guards continue to decide effective placement. The raw
source-inventory table is separate from physical identity and health totals.

`prepare-scoped-inventory.mjs` builds an offline review plan. Explicit source-only
replacement pairs are required to generate those operations. `scopedStatements`
produces private dry-run, apply and rollback SQL; it has no database/network path.
Keep actual source files, mappings, before snapshots, actor IDs, authorization
evidence and generated SQL outside git. A derived-map hash is never represented
as the original CSV byte hash.

Before application, deploy and verify the compatible reader, install the reviewed
schema candidate, and refresh the base/scoped revisions, exact before records and
binding guards. Run the dry-run in a transaction that rolls back; compare every
changed row and unchanged operational state. Application is a separate reviewed
step. Rollback requires the exact current base, scoped revision and active request
ID, advances the revision, and retains every batch and audit entry. Rolling back
or replaying a stale request cannot overwrite a later scoped change.

Local database tests use synthetic PGlite fixtures, including SQL generated by the
offline preparer. Projection and presentation tests cover newer Owner evidence,
source-only replacement, no-IP Shop inventory, lifecycle retention and unchanged
health/endpoint data. Browser coverage is in `sniper-inventory.browser.spec.mjs`.


## Four-family extension (existing overlay upgrade)

The additional exact categories are `Spotter`, `Spotter HD`, `Spotter HDC2`,
`Spotter HDC4`, `Solar Spotter`, `RANGER 1 CAM.`, and `Helios Solar Tower`. Only existing bound ProductIds are admitted;
`replace_source_hold` remains unavailable for these families. Assignment keeps
its exact source label (including existing trailing whitespace). A separate
`source_label_correction` changes only `after.unitNumber`, requires its parsed
family/decimal identity to equal the existing binding canonical key, and rejects
another record with that key or parsed label. Decimal suffixes are strings, never
rounded. Physical binding labels, native/tracker IDs and DO NOT USE markers remain
intact. The snapshot updates only the binding source `fullLabel` to match the
corrected source label, satisfying the existing projection validation contract.

Four-family operations require an `authority` object with `kind`
(`service_item_export` or `user_override`), `libraryFileId`, `sha256`, `receivedAt`
(with timezone), and `authorizationSha256` matching the batch authorization.
Only a user override can carry optional `effectiveAt`; it cannot be future to
its receipt or regress an earlier effective time. Do not invent an effective
time for a correction without one. Assignment authority is retained as
`assignmentAuthority`, and `scopedAuthority.receivedAt` uses that authority's
actual source `receivedAt`, never the later batch preparation time. Receipt time
and effective time are distinct. Label-only evidence is saved separately as
`sourceLabelAuthority`; existing `scopedAuthority` and `assignmentAuthority`
remain byte-for-byte unchanged (or absent, retaining the original base receipt).
An intervening Owner customer/placement correction therefore continues to win
over an older source assignment, even if the batch or label review happens later.
An export cannot supersede a saved user override without explicit user review.

Company matching trims/collapses whitespace and ignores case, admitting only
Cameras Onsite LLC, Cameras Onsite, Cameras OnSite and Cameras On Site. SHOP also
requires a company customer ID from the original reviewed receipt. Other named
customers require FIELD and a non-company ID; unknown/unassigned/review values
fail closed for separate review. An assignment cannot attach a customer name to
a company ID and merely flip the Shop flag.

Optional `sourceAddress` and `sourceAddressEvidence` must appear together, outside
`after`. The address has exactly four nonempty string fields: `street`, `city`,
`state`, `zip`. Evidence has `kind`, `libraryFileId`, `sha256`, `sourceProductId`,
`customerId`, `receivedAt`, `authorizationSha256`. `service_item_export` evidence
must refer to this ProductId; `user_confirmed_customer_address` may cite a
different source row for the same customer only with a user override. The
customer ID must equal the target assignment. Hashes refer to the actual source
bytes, not the derived mapping; the administrator must independently inspect
the cited source and user authorization. SQL validates the attestation envelope,
not remote Library contents. Customer changes without address evidence clear the
old address and its provenance. No address is written to installation/GPS tables.
Exact historical customer/address data survives in the original receipt, previous
immutable scoped batches and each operation's `expectedRecord`.

### Required production review and migration steps

1. Keep source/customer data and executable operation payloads outside git.
   Obtain fresh exact scoped records, current base hash, scoped revision/head and
   identity guards. Confirm the already applied corrections remain untouched.
   Do not replace the base upload or rerun a prior inventory batch.
2. For an already installed overlay, extract **only** the complete
   `CREATE OR REPLACE FUNCTION ...review_scoped_inventory(...) ... end $$;`
   statement (ending before `rollback_scoped_inventory`) and the complete
   `CREATE OR REPLACE FUNCTION ...upload_snapshot() ... $$;` statement (ending
   before the final revoke). Review and install those two function definitions in
   one transaction after parent approval. Do not run
   the whole bootstrap file: tables, triggers and the preserved reader already
   exist. Capture both old function definitions first for code rollback. Compare
   function OIDs, owners, ACLs, invoker security and configuration before/after;
   no grant is required. PGlite and PostgreSQL upgrade tests install the actual
   PR176 SQL from commit `916129fcc09049cffdd2c519f67b2ef95e5d3587`, create revision
   one under that function, then verify the two-function upgrade preserves those
   properties, saved batches/audit/control, records and snapshot.
3. Build the explicit bounded operations using the above contract. The existing
   Sniper-only offline preparer is unchanged and must not generate this batch.
   Independently verify each address from the latest export or confirmed customer
   source; user corrections override contradictory export assignments. Use only
   the specified unit's effective time. Clear obsolete addresses when a Shop
   return has no independently supported company source address.
4. Under the existing Owner actor/admin transport, call with `p_apply=false` in
   a rollback transaction. Verify the expected membership and exact changed rows
   from source data, not fixed totals. The base/control row locks serialize scoped
   reviews; NOWAIT SHARE locks reject concurrent identity/operational writes.
   The independent PostgreSQL test observes real lock waits in `pg_stat_activity`
   across four sessions, covering competing applies, rollbacks, base changes,
   identity NOWAIT rejection and delayed identity writes followed by drift rejection.
5. Application is a separate parent-reviewed action using the identical payload,
   exact revision and unique request ID. Compare all untouched records, bindings,
   endpoints, lifecycle, source dates, tracker/native tables, provider links,
   installation/GPS/history and base receipt. Health publication and tracker
   updates are separate work. No refresh, status or Fleet change is included.
6. Data rollback uses the existing rollback function with the then-current base,
   revision and active request ID; revision increases and evidence stays immutable.
   Code rollback restores the two captured prior function definitions only.

Synthetic validation: from `tech-checks/operations`, run
`node --no-wasm-code-gc --import tsx --test --test-concurrency=1 tests/scoped*test.mjs`.
The V8 flag avoids a Node/PGlite WASM code-GC crash observed in this environment;
it does not change SQL behavior.
