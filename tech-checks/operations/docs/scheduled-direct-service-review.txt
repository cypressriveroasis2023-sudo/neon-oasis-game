Scheduled Sniper / CAM V service checks: local review candidate

Scope and observed cause
The read-only camera-health-sweep v51 capture is the scheduled path. Its selector excludes deactivated devices and Root/Shop organizations before probing. That directly excludes the twelve saved endpoint-bearing gap records. Two additional gap records lack an endpoint and remain held. Saved captures do not establish current monitoring_enabled/profile flags; this patch never invents them. Across the entire captured direct-family graph, 184 source rows comprise 169 uniquely paired owned records with saved endpoints, six missing endpoints, three missing/ambiguous pairs, one foreign match and five retired rows. The 179-endpoint performance cohort is a synthetic upper capacity case, not a live eligibility claim.

The existing cron runs at minutes 0, 15, 30 and 45, with a 55,000 ms HTTP timeout. The provider-reconcile jobs cover Witness, Vigilant and Reconeyez; no direct Avigilon cron was captured. This candidate repairs the scheduled sweep, with no new job or schema.

Eligibility
An exact full-family label must uniquely join one equipment_master row and one camera_devices row. Families are CAMV, Sniper, Sniper 2 and Sniper 4. Case/spacing and CAM V/CAMV spelling may normalize, but digits, leading zeros and family variants never collapse. Device source must be 2026_unit_tracker, monitoring must be enabled, profile must agree with the family, and both saved revision and configured public IPv4/port list must validate. No endpoint defaults, DNS lookup, router fallback or IP-based identity. Disabled/foreign-profile duplicates remain visible to the identity check. Truncated inventories fail closed at 1,000 rows.

Both Shop and Field are eligible. Explicit retired, decommissioned, stolen, DNU, do-not-use and not-in-use indications are held. No placement, activation, owner, source or identity write occurs. The source/device eligibility is reread after probes, before publication. Initial identity reads include all Sniper/CAM-like keys across every ownership/profile/monitoring state. Per-wave reads use validated family/tag filters and broad full-key ILIKE patterns, then strict normalized identity checks. These patterns preserve mixed case/whitespace aliases and disabled/foreign duplicates while limiting returned rows. Known ownership, terminal lifecycle, full-family identity, duplicate, endpoint or revision changes decline the observation. Shop/Field movement alone does not invalidate an unchanged endpoint observation.

Publication and remaining race
The deployed publish_camera_connection_v1 seven-argument signature and SQL remain unchanged. Its atomic endpoint-revision/IP/ports/profile/monitoring-enabled CAS and newer-observation rejection remain authoritative. The exact captured pg_get_functiondef SHA256 is ade4074d7fbbb2b0023a098c47cb7ff5a69ca08125d91208939615c408a2644a; owner postgres; SECURITY DEFINER; search_path=pg_catalog, public; ACL postgres/service_role only. No new grants or private-schema access.

Source/terminal-lifecycle edits committed after the final reread remain an acknowledged race under the existing RPC. Such a write can still save historical service evidence for the original endpoint, but cannot move or reactivate a record. UI lifecycle rules remain authoritative. An HTTP timeout during publication has an uncertain commit outcome: the handler reports unknown, does not retry, and never synthesizes another failed check. A committed row, if any, contains the actual observation sent before the timeout. Skipped/invalid/eligibility-held observations make no publisher call and do not increment counters.

Evidence semantics
Only saved service/port connectivity is recorded. A reachable service never fabricates individual camera or channel health. The observation timestamp is the actual completion time, retained through rereads/publication. Genuine failures use the prior proof for the same endpoint/revision. Existing long-gap failure-counter behavior is retained: there is no new age reset for a prior failed proof. This work does not claim to fix that behavior. Malformed, stale, auth-failed or incomplete results stay unverified. No live endpoint has been probed during this work.

Budget and continuation
Ten camera groups run per wave; each uses only its saved ports concurrently, with a 2,200 ms socket deadline. The camera request-relative deadline is 48 seconds, and no new wave starts with less than 3.2 seconds remaining. Every camera read/RPC gets an AbortSignal and a maximum 4-second timeout, shortened to remaining budget. The shared HTTP client bounds auth/router/heartbeat transport to four seconds and the request-relative 52-second boundary. Router checks run alongside cameras; their eligibility, management-port choice and exact configuration CAS stay intact. Transport failure returns unknown, not an outage.

Missing and known-held identities are removed before queueing. One rotating ten-candidate window is reserved each 15-minute slot; remaining work is oldest-first. Unfinished records retain their timestamps. Even if the oldest records remain held, the reserved window reaches the full 179-candidate capacity cohort within 18 scheduled slots; ordinary successful sweeps attempt the whole cohort each run. Slow metadata or publisher services can cause partial coverage; returned deferred/held counts expose that condition.

The normal 15-minute schedule exceeds the documented maximum Edge worker lifetime (150 seconds free / 400 seconds paid), so normal scheduled invocations do not overlap. There is no persistent lease. Simultaneous manual or duplicate invocations can still repeat probes and contend on the existing publisher; newer-result CAS remains in force. This is an explicit limitation.

Deno currently documents AbortSignal on ConnectOptions. The transport additionally races an explicit timer and closes late successful sockets, so the handler timeout does not depend solely on signal support. Actual hosted runtime cancellation and CPU use have not been measured by local tests.

Coverage heartbeat
Every authorized completed attempt now writes an explicit Avigilon monitor summary, including zero-publication and collector-failure runs. Metadata records eligible, held, deferred, scanned, acknowledged published, unverified, deadline_reached, complete, reasons, held_reasons and unverified_reasons. Any held/deferred/unverified work produces the existing partial status and complete:false. A collector failure uses null counts and counts_known:false instead of inventing zero coverage. Complete coverage alone uses ok. If the bounded metadata write fails or cannot fit its deadline, the response is 503 with coverage_recorded:false; no successful persistence is claimed.

The existing integration column is text and provider-reconcile already writes partial. The current legacy diagnostic reader treats failed/error providers as unavailable and tolerates partial plus additive metadata. Native Recon identity reads are scoped to the reconeyez provider; the Avigilon summary does not change its proof. Service and camera health remain driven by their original evidence, never by this integration status. Focused tests exercise incomplete, complete, zero-publication, collector-error and heartbeat-error outcomes and the actual legacy diagnostic reader.
