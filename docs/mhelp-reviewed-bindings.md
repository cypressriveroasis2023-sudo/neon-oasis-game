# Reviewed mHelp publisher bindings (staged, not applied)

The publisher must preserve a reviewed combined `customer: site` cell instead of converting it to the parent customer alone. A binding stores `customer_style` (`plain` by default, or explicitly reviewed `combined`) so the format survives a Shop round trip. Runtime and PostgreSQL stage validation compute the same exact authoritative value; equivalent existing spelling is preserved. Product ID, source freshness, manual-change, native and pending-write guards remain in force.

`review.ts` is a pure, non-executing review planner. It requires two identical Sheet snapshots, exact Product-ID index/source matches, unchanged cell metadata, current native authority, no source review flag or operational override, and no pending intent. It retains direct holds and propagates occupied destinations. It produces a safe vacant-ended row order and holds cycles. Every result says `approvalRequired: true` and `executable: false`; source freshness is reported separately.

`mhelp-publisher-reviewed-bindings.sql` defines the style column, matching stage guard and an admin-only repair function. Installing it performs no row repair. Do not install or invoke it as part of the already-completed PR299 release. The repair function requires a recently read, explicitly reviewed exact before/after manifest and a one-use authorization hash, locks publisher/native/source state, rejects pending work and changed evidence, rechecks fresh observations and API holds, and records before/after evidence in a private audit table. It updates only publisher bindings. It never changes equipment, Sheet data, provider identities, credentials, IP/SIM, physical addresses or history. It never deletes/reinserts bindings, weakens uniqueness or uses temporary fake identities. Occupied/cyclic destinations abort the entire transaction.

The admin caller must obtain approval for the refreshed list, perform two identical live Sheet reads, and verify the explicit review authorization before calling the function. The database cannot itself fetch Google Sheet cells; it enforces the two-minute evidence window and exact saved binding/source/native state. A changed Sheet after the reads will still be held by the publisher's normal exact-cell check; this is not a claim of Google compare-and-set semantics.
